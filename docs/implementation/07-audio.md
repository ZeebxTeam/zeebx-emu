# 07 — Audio

## What games deliver

**Effects are WAVE; music is not.** That is the split, and it explains a symptom that lasted a
long time: sound effects played in every game and music played in none. It was not a defect in
the mixer — two whole formats were missing.

Counted in the packages of the sixty-three titles:

| Format | Where it shows up |
|---|---|
| RIFF/WAVE | sound effects, in 14 games — always played |
| **MP3** | the music of 9 games: Quake, Quake 2, Galaxy on Fire, Rally Master Pro, Powerboat Challenge, Action Hero 3D, Need For Speed, zeetris and the Z-Wheel |
| **MIDI** | the music of the arcade ports: Double Dragon, Bad Dudes, Caveman Ninja, Dark Seal, Heavy Barrel, Karnov's Revenge, Magical Drop 3, Spin Master, Street Hoop, Super BurgerTime and Wizard Fire |
| **PCM generated by the game** | the Data East arcade ports again: the sound of the emulated board comes out through an `ISource`, see below |

The survey comes from reading the packages, not from assumption: the arcade ports carry **one**
`.wav` each — the effect — and their music arrives through `IMedia` as MIDI, which the report
said in a line that was easy to miss, `sound rejected (audio/mid)`.

MP3 already plays (see below). MIDI is the subject of the end of this page.

`audio/wav.rs` reads:

- 8-bit PCM (unsigned, centered on 128) and 16-bit PCM (signed);
- **IMA ADPCM** (format 17), which is what Pac-Mania uses.

An unknown format is refused **by number**: `WavError::NotPcm(tag)`. A sound that disappears
without explanation turns into a hunt; an error that says "format 85" turns into a line of
research.

## The BREW path

```
IMediaUtil::CreateMedia(AEEMediaData { clsData, pData, dwSize })
        │
IMedia::SetMediaParm(MM_PARM_MEDIA_DATA | VOLUME | MUTE | PLAY_REPEAT)
        │
        ├──► on the next pass of the loop, reads the bytes and decodes the WAVE, the MP3 or the MIDI
        │
IMedia::Play  ──►  voice in the mixer
```

The identifiers (`MM_PARM_MEDIA_DATA = 1`, `MM_PARM_VOLUME = 4`, `MM_PARM_MUTE = 5`,
`MM_PARM_PLAY_REPEAT = 11`, `AEE_MAX_VOLUME = 100`, `MMD_FILE_NAME = 0`, `MMD_BUFFER = 1`) come
from `AEEIMedia.h`.

**The buffer is read on the next pass of the event loop** (`Machine::resolve_media`, called in
`deliver_signals`), and the cache (`MediaPayload`) is keyed by **content**. The two extremes break
different games:

- **Read at `Play`**, with a cache keyed by `(address, size)` — as it was for a long time —, a
  game that loads several sounds through the same scratch buffer has already reused it by the time
  it plays, and a new sound at the same address with the same size played the old one.
- **Read at delivery** — the first fix, which came from the comparison with zeebulator3 —, Zeebo
  F.C. Super League delivered the menu navigation sound with only the WAV header written: it
  delivers, asks to play and copies the samples right after, in the same handler. Out came a hiss
  with the buffer's old contents, which even included the header of an ATC texture.

The loop pass sits between the two: the game's handler has finished writing and has not yet
reused the buffer. On the device `Play` also only reads later, in a separate task. A `Play` on a
sound not yet read marks the object as playing, notifies the start and starts the voice when the
buffer is read; `GetTotalTime` forces the read on the spot, because whoever asks needs the
duration.

Three forms of delivery:

- `MMD_BUFFER`: memory. A buffer that starts with the gzip signature (`1f 8b`) is decompressed
  first — Double Dragon's `sound.ggz` is stored this way.
- `MMD_FILE_NAME`: the name of a file in the package, read through the virtual file system.
  Galaxy on Fire delivers its seven songs this way (`GalaxyOnFire1_Theme.mp3` and the others), and
  before they were silently refused. A file that does not exist answers `EFAILED` and goes into the
  report.
- `MMD_ISOURCE` is only played as raw PCM: an `ISource` that delivers a compressed file stays
  silent.

The classes of the SDK's `AEECLSID_MULTIMEDIA` family all create the same object: QCP, PMD,
MIDIOUTMSG, MIDIOUTQCP, MPEG4, MMF, PHR, AAC, IMELODY, AMR, XMF and DLS, plus MEDIA, MIDI, MP3,
ADPCM and PCM. The content goes through the decoders we have, and what none of them reads ends on
the spot. QCELP and EVRC are not decoded here nor in zeebulator3.

`RegisterNotify` is honored: the game receives `MM_STATUS_START` when the sound starts and
`MM_STATUS_DONE` when it ends, in the 28-byte `AEEMediaCmdNotify` from `AEEIMedia.h`. Without that
notification, a game that only plays the next sound when the previous one ends goes silent after
the first.

**`START` and the natural end go out on the loop pass, not on return from `Play`**
(`Machine::deliver_media_notifies`, in `deliver_signals`). The Zeebo Extreme games depend on this.
Their sound manager (`SoundMgr`/`SoundPlayer` from the TTD library) marks the sound as "requested"
(2) **after** `Play`, and `START` moves it to "playing" (1). With the notification on return from
the call, `START` arrived before the mark and the sound stayed at 2 forever. Their `Stop` only
acts on 1, so the menu music never stopped. The track music sat in the queue waiting for the
channel (`+0x3634` in the player), and with music queued the player refuses every effect: Bóia
Cross raced with only the soundtrack, without a single sound call. The notification block is
written at the moment of each delivery, because a `START` and a `DONE` for the same object on the
same pass share the block.

**Every notification goes out this way, including the `DONE` from `Stop`, and it does not vanish
with `Release`.** Double Dragon repeats the music through `DONE`: if the object is still marked,
it schedules a `Play` 100 ms later. It unmarks and releases the object right after `Stop`; with
`DONE` on return from `Stop`, the handler still saw the object marked, and the scheduled `Play`
landed on an already freed `IMedia` — address zero, on pressing back. Zeebo F.C. Super League, on
the contrary, stops and releases and **waits** for that sound's `DONE`: if the notification were
discarded along with the object, the intro would stop on the notice screen. That is why the
handler is stored when the notification is born, and delivery does not depend on the object
existing.

**A sound delivered through memory is reread on every `Play`.** The device's `IMedia` does not copy
the buffer. Super League has a single object for the match effects, with a 500 KB buffer: it
writes the kick or the step and asks to play again, without another `SetMediaParm`. Kept from the
first read, every effect came out with the menu select sound, the first one to go through there.
The reread follows the rule above — on the loop pass — and the content-keyed cache avoids decoding
again what has not changed.

`Stop` on a sound that was playing also notifies, **with `MM_STATUS_DONE`**. That was what left the
Crash Nitro Kart races silent. It counts the active sounds and only plays the track music when the
count reaches zero; its notification handler (`0x11a80`) decrements on `DONE` (2) and on status 9
and **ignores `ABORT` (3)**. On entering the race it stops the menu songs with `Stop`: with no
notification at all, and later with the `ABORT` that zeebulator3 uses, they never left the count,
and the whole race — countdown, engine and the 642 KB soundtrack — went without a single `Play`.
With `DONE`, the countdown plays at 31 s, the soundtrack goes into repeat and the engine changes
sound with the revs.

**The WAVE ends where `RIFF` says.** Zeebo F.C. Super League builds sounds in a 500 KB scratch
buffer and writes the size of the whole buffer in the `data` chunk, but the size of the sound
(14 KB) in `RIFF`. Following `data` played eleven seconds — the effect and then memory garbage,
loud, over the music. When `data` goes more than 4 KB past the end `RIFF` declares, `RIFF` wins; a
difference of a few bytes is an edited file with a stale `RIFF`, and cuts nothing. While sounds
were read at `Play`, that buffer already had other contents and the defect did not show.

**But `RIFF` is a reading of one instant, and Turma da Mônica writes after it.** The game's voice
lines are Ogg, decoded by the game itself (it ships Tremor) into an 882,000-byte buffer whose
header comes from a template: `RIFF` of 56,352 (0.638 s, the size of `sfx_bal_all.wav`) and `data`
of the whole buffer. `RIFF` never changes. At `Play` there are about 0.2 s decoded, and the rest
arrives some 0.3 s ahead of what is playing. Read all at once and cut at `RIFF`, the line lasted
0.638 s; `DONE` arrived, and the game cleared the buffer and stopped decoding — the sound died at
the start.

That is why a WAVE whose `data` goes past `RIFF` plays **reading the game's buffer while it
plays** (`Machine::open_live_buffer`), and only grows beyond `RIFF` with what gets written there
**after** `Play`. Super League's garbage was already there and does not count; Mônica's line does.
The end is projected at the end of what has been written plus 0.3 s, but what ends the line is the
game itself, with `Stop`: measured, `prof_sel_mon_01` (4.71 s) receives `Stop` 4.72 s after
`Play`.

This page once recorded `sfx_bal_all.wav` as **proof** of the `RIFF` rule for this buffer. It was
not: the 0.63 s effect is just the header template, and the lines that go through there are up to
five seconds long.

To check without listening, `zeebx session <zip> --dump-audio=A.wav` records the mix of the
window's session, at the pace of the virtual clock.

A `Play` on a sound that is still playing does **not** notify. Notifying caused a loop in games
that play again inside the handler: the new `Play` landed on the sound that had just started,
generated another notification, and the sound restarted every frame — Zeebo F.C. Super League came
out clipped and choppy.

**A `Play` on music already playing in a loop does not restart it.** The Zeebo Extreme sound
manager asks to play the track music again every time an effect ends: in Rolima, the 10 KB effect
plays, receives `Stop`, and the `Play` lands on the 807 KB MP3 that is already on infinite repeat.
The voice restarted from the beginning, and the music restarted on every boost and every drift.
Refusing with `EBADSTATE` does not work: the game understands the music stopped and repeats the
`Play` every frame. What it expects is `START`, which moves it to "playing"; the voice carries on
from where it is. The rule applies only to the infinite loop (`MM_PARM_PLAY_REPEAT` zero), because
an effect played again over itself is what Zeebo F.C. does, and it needs to restart.

**The decoded sound cache has a ceiling.** Past 64, the ones no `IMedia` uses are dropped. Without
this, every new content written to Zeebo F.C.'s scratch buffer stayed decoded forever. A playing
voice loses nothing: its PCM is in an `Arc` that the mixer also holds.

`GetMediaParm` returns the stored volume and mute (before, zero: a game that reads the volume and
writes it back muted itself), and a released `IMedia` stops its voice in the mixer — a song on
repeat kept playing after the object was gone.

`IMedia::GetState` returns the object to "ready" when the sound has ended — that is what the game
queries to know it can play the next one. **What says it ended is the virtual clock, not the
mixer**: the emulator runs muted without ceasing to count time, and there is sound that plays in
silence because we know how to time it without knowing how to decode it.

## The mixer

`audio/mod.rs`. Each `Voice` has a position, a step, a volume, how much is left and whether it is
paused. The step is the ratio between the sound's rate and the card's: that is how an 8 kHz WAVE
comes out right on a 48 kHz output. There is a zero-crossing test proving that resampling
**preserves pitch** — getting this wrong gives a sound that plays, seems fine, and is in the wrong
key.

Finished voices are collected inside `fill`, in the same place they are consumed. The output is
`cpal`.

In fast-forward the step of each voice and each stream is multiplied by the speed the game reached
(`Mixer::set_fast_forward`): sound is pulled by the card's clock, and without this the music
stayed at 1x with the game at 3x. See [24-speed.md](24-speed.md).

**Pausing the window freezes the mixer** (`Mixer::freeze`, called by `RunningGame` in egui and Qt
and by `Emulator` on Android). Before, pause only stopped the game: the audio thread kept pulling
the voices, and the music went on with the picture frozen. Since what says a sound ended is the
virtual clock, and pause holds it, the music could end during the pause and, on return, the game
waited for a sound that no longer existed. Streams (`Stream`) did not have the defect: the stopped
game does not feed them, and the queue runs dry. Frozen, `fill` advances neither voice nor stream;
entering and leaving go through a ramp of `FADE_OUT_FRAMES` frames, because stopping in the middle
of the wave clicks. It is not mute, which lets the sound run, nor the rewind silence, which swaps
the sound for that of each point.

## How to check without listening

`--dump-audio=file.wav` records the mix. That is how the implementation was verified: peak of
0.700 in Quake, 0.807 in Double Dragon, 1.000 in Peteca, 0.586 in Pac-Mania, with the expected
proportion between blocks with sound and blocks of silence.

It does not replace listening, but it separates "no sound comes out" from "wrong sound comes out".

## The MP3 that didn't play, and the game that insisted

Tekken 2 was classified as "too slow": it made **766 thousand `Play` and 766 thousand `GetState`
calls in four virtual seconds**, and six seconds of game did not finish in five minutes of
machine time. It looked like a heavy game.

It was not. The trace shows the pair repeating with nothing in between:

```
IMedia::GetState → 2   (MM_STATE_READY)
IMedia::Play     → 0
IMedia::GetState → 2
IMedia::Play     → 0
```

The music is MP3, `audio/wav.rs` refuses it, and `Play` fell into the "no readable sound" path,
which told the game that **the sound had already ended**. The game queried the state, saw
"ready", and asked to play again. Forever.

The first fix was not a decoder. It was `audio/mp3.rs`, which reads the header of the first frame
and the encoder's `Xing`/`Info` tag and returns **only the duration** — when the tag carries the
frame count the number is exact even with a variable bitrate; without it, what is left is size
divided by bitrate. With the duration, the sound "plays" in silence for the right time on the
virtual clock, `GetState` answers "playing" meanwhile, and the game moves on.

It was a declared trade-off, and it showed up in the report as an assumption in use: **Tekken
moved, silent**. Six virtual seconds went from more than five minutes to **9.7 seconds**, and it
draws the title screen. What is left in it now is another matter: 1.08 million `DrawPixel` per
frame, which is API dispatch cost.

## The MP3 that now plays

The duration solved the hang but not the music, and the music belongs to nine games — not one. So
`audio/mp3.rs` gained `decode`, which returns the same `Sound` that RIFF/WAVE produces: the mixer
does not know where the sound came from, and resampling, volume and repeat work the same.

The decoding itself is done by **symphonia**, pure Rust, only MP3 enabled. It is the same decision
as SQLite for `ISQLMgr` and `ab_glyph` for `DrawText`, and it is worth saying why: Layer III is
Huffman, requantization, joint stereo, IMDCT and a polyphase synthesis filterbank, and writing that
without a reference to compare the output against gives the worst possible result — sound that
plays, seems fine and is wrong.

Order in `machine/media.rs`: RIFF/WAVE first, because it is what almost every sound is and the
cheapest to recognize; MP3 next; and only then the refusal, which still names the format. The
duration path stayed as a safety net for an MP3 the decoder refuses.

The verification, measured:

- The 440 Hz test tone decodes with **a peak of 0.761 and a pitch of 440 Hz** — the pitch is
  checked by zero crossing, because a wrong pitch would pass any other check. The output matches
  the reference decoder's to seven decimal places.
- **Tekken 2** went from silence to **71.6% non-zero samples** in eight seconds, with a peak of
  0.698. The "Tekken stays silent" assumption left its report.
- Decoding is done **once per content**, at delivery: the result goes into the sound cache in
  `machine/media.rs`. A thirty-six-second track at 22 kHz mono is six megabytes of `f32`, and none
  of our games changes music often enough to justify streaming.

The lesson goes beyond audio: **before optimizing a slow game, check whether it is working or
insisting.** Heavy Weapon was the same case, with bitmaps that measured 0×0.

## MIDI, which is not decoded: it is synthesized

`audio/midi.rs`. Eleven games deliver their soundtrack as MIDI, and **MIDI is not sound, it is a
score**: there are no samples in the file, there is "play note 69 on instrument 25 with velocity
100". What turned that into sound was the console firmware's synthesizer, with its instrument
bank — which is in the part of the NAND we have not read yet.

So what comes out of here is a **declared approximation**, and it shows up in the report as an
assumption in use. Saying so plainly matters more than usual, because in this case the error is
silent: wrongly synthesized music *plays*, and sounds as if that is how it is.

That is why the module only holds itself to what can be verified without listening — **the right
note, at the right time, for the right length**:

- **The score, as the specification says.** Formats 0 and 1, several tracks merged by tick,
  running status, `Note On` with zero velocity counting as `Note Off`, meta and SysEx skipped by
  their declared length. Running status is not an optimization: a track of consecutive notes is
  almost entirely written that way, and ignoring it does not lose one event, it loses the whole
  track from the first one on.
- **Tick to second**, honoring the header's division and each `Set Tempo` from its point onward —
  recomputing the whole song with the new tempo puts everything after an *accelerando* in the wrong
  place without anything looking broken. SMPTE division counts too: the high byte is the frame
  count in two's complement, and negating all sixteen bits together gives 24 where it should give
  25.
- **Tuning.** Note 69 comes out at 440 Hz, and the test measures this by correlation with the
  right tone and with the two neighboring semitones — counting zero crossings depends on the
  waveform, correlation does not. Wrong tuning is the defect that most easily passes for "the
  synthesizer is like that".

What is a guess, and a guess for lack of data: **the timbre**. The table maps General MIDI family
to waveform and envelope, trying to get the *behavior* right — piano decays, organ sustains, brass
attacks slowly —, because that is what makes the melody recognizable even with the wrong
instrument. Percussion is filtered noise, with two decay families separating kick from cymbal.

Two precautions that are not details:

- **Square and saw are summed from harmonics** up to below Nyquist, not generated from the raw
  shape. A raw square at 22 kHz aliases: the harmonics above half the rate fold back as frequencies
  that are not in the score, and the note comes out with a whistle that rises when it falls.
- **The peak is normalized to 0.8.** Summing dozens of voices easily goes past 1.0, and what goes
  past clips — and clipping sounds exactly like "the synthesizer is bad", without being so.

Measured on Double Dragon: the `sound rejected (audio/mid)` line left the report, and ten seconds
of game went from silence to **74.7% non-zero samples**, with a peak of 0.807.

### Double Dragon's MIDI, measured against Zeebulator

Double Dragon was the first serious exception to "the approximation is enough". Compared with the
other emulator, its sound is poor — and the investigation showed the cause is structural, not a
tweak.

**The package carries MIDI, and it was hidden.** A `grep` for `MThd` in the zip finds nothing:
`sound.ggz` (1,928,097 B) is a 592 B header with **74 pairs** `(offset, size)` and 74 contiguous
gzip members. With all 74 checked, the declared size matches in every one, and the content is
**62 `RIFF`/WAVE** (effects, mono 16-bit 22,050 Hz) and **12 `MThd`** (songs). The main BGM has
1,788 notes, 47.47 s, 9 channels and 404 percussion events; the 12 add up to 22,729 notes.

**What the score asks for** (and this is where the approximation hurts most):

| family | share of notes |
|---|---:|
| pianos (0–7) | 28.7% |
| **guitars (24–31)** | **23.2%** |
| percussion (channel 10) | 20.6% (4,681 notes) |
| brass | 9.2% |

**Zeebulator turns that into sound with samples, not waveforms.** It loads a real General MIDI
soundfont (GeneralUser GS, **32,319,396 B**) and plays with **TinySoundFont** (MIT, `tsf.h`), in
mono at 22,050 Hz and with **−16 dB** of headroom before `tsf`'s internal clipping. Note On/Off,
`Program Change` and percussion go to the bank: channel 10 uses the soundfont's own kit (bank
128), not a classification of ours.

**The controlled comparison**, same note and same length, passing the same file through both
implementations (and through an independent reference, `timidity` + `FluidR3_GM`):

| render | H2..H8 / H1 | centroid | 85% rolloff |
|---|---|---:|---:|
| Zeebulator with soundfont | 1 · .27 · .015 · .072 · .018 | 1383 Hz | 2647 Hz |
| `timidity` + FluidR3 | — | 1638 Hz | 3140 Hz |
| **Zeebx (`midi.rs`)** | 1 · **0** · .012 · **0** · .002 | **1065 Hz** | **1174 Hz** |

In other words: ours comes out **darker and poorer in harmonics** than both soundfont renders,
with the right tuning (441.0 Hz measured against 440.0 — an error of +0.23%, no octave error). The
problem is the **material**, not the pitch.

And the most visible defect is this one, measured program by program: **29 (overdrive guitar), 30
(distortion), 42 (cello) and 48 (strings) come out with the same waveform** — the table maps
family, and family `24–31` is "saw with decay". 81 (lead saw) comes out **square** where the score
asks for sawtooth. The bass (33) stays **flat at 0.65** until the end, where the soundfont decays
to 0.27. In the guitars that is 23.2% of the game's notes.

Measured over the whole song:

| render | peak | RMS |
|---|---:|---:|
| Zeebulator with soundfont | 25,727 (78.5% FS) | 4,877 |
| Zeebulator without soundfont (fallback) | 32,767 (**100% FS**, clips) | 8,401 (+4.72 dB) |
| Zeebx (`midi.rs`) | 0.799988 (= 0.8 by construction) | ≈4,782 |

**A caveat that avoids a wrong conclusion:** in **upstream** Zeebulator **the soundfont is only
wired in `tools/game_probe.cpp`**. `frontends/standalone/main.cpp` builds `MediaHle` without it, so
it falls back to the crude synthesizer — which is *even darker* (880 Hz rolloff). Anyone comparing
through the standalone is not hearing any soundfont; the binary with the bank is `game_probe`.

**License: Zeebulator's code is now compatible with the project's license.** It is **GPLv3** and
Zeebx is **GPL-2.0-or-later**. The common path still uses what is under its own license:
**TinySoundFont** (MIT), `rustysynth` (MIT, pure Rust) and the GeneralUser GS bank itself
(permissive license, although its text admits the unknown origin of some of the samples).
`oxisynth` is LGPL-2.1 and stays out.

**The cost, measured:** the bank is **10.3×** the size of Zeebulator's whole tree, takes **+64 MiB
of RSS** on load (`tsf` converts everything to `float`) and would take the core's `.so` from
**15.6 MB to ~48 MB** across six CI targets. Zeebulator's compiled-in absolute path does not work
for the core: it is not relocatable, it leaks the build's `$HOME` and, with the file missing, the
music degrades into silence.

**Two facts that change the risk of the swap:**

1. Swapping the synthesizer **does not flag a regression in the baseline** of the 62 ROMs: peak
   and RMS are in the full report and **not** in the summary, by a decision recorded in `scan.rs`
   — checked, `0` of the 62 files in `docs/scan/` have the `audio:` line.
2. On the other hand, **17 tests** inside `src/audio/midi.rs` pin properties of the current
   synthesis (peak in `0.79..=0.81`, pitch by correlation, percussion brightness). An engine swap
   rewrites them.

The plan, in two stages, with the measurement in between:

- **Stage 1, cheap:** fix in the table exactly what was measured — sustained guitars 24–31 (29
  and 30 are 23.2% of the score), 81 as sawtooth, bass without flat sustain, and separate 42 from
  48.
- **Stage 2, faithful:** GM wavetable with a compatible license (`rustysynth`, MIT), with the bank
  as an **optional file next to the core** and fallback to the current synthesizer when it is
  missing — the Libretro core cannot gain a host dependency, and 32 MB embedded in every `.so` does
  not pay for itself.

The comparison harness lives outside the repository, in `~/zeebx-midi-harness`: `zbfont/` (C++
with `tsf.h` and the bank), `zxmidi/` (our `midi.rs` in a minimal crate) and `abtest/` (the WAVs
for each case). It is what measures each step instead of offering opinions.

## The sound the game generates while it plays

The Data East arcade ports do not deliver a file: they emulate the board's sound chip and produce
the samples frame by frame. The delivery is an `AEEMediaDataEx` with `clsData = MMD_ISOURCE`
(`0x01001012`), `bRaw` set, an `ISource` the game itself implements and an `AEEMediaWaveSpec` with
the format — 11025 Hz, mono, signed 16-bit, in the ones measured.

While we only knew how to read memory and files, the delivery was refused and the game's log said
`Failed to SetMediaDataEx!!!!`: **none** of the eleven ports had sound. Now the delivery is
recognized, and `Play` opens a stream voice in the mixer.

**The virtual clock sets the pace.** On each loop pass the emulator computes how many frames the
clock already owes, with a tenth of a second of lead so the card does not run dry between two
passes, and calls the game's `ISource::Read` until it gathers that — at most a few reads per pass,
because a `Read` that returns less than was asked is the game with no samples ready. It is the
same choice as the rest of the sound: with no card at all the emulator keeps asking, and the game,
which emulates the sound chip inside `Read`, moves along the same way.

The stream voice lives in `audio/mod.rs`, next to the voices of ready-made sound. It resamples to
the card's rate by interpolating between two frames, keeps at most half a second — if the game
delivers faster than the card consumes, the oldest excess is dropped instead of the latency
growing — and, when a sample is missing, holds the last value instead of clicking to zero.

### Stage 1 done: the timbre table redone against the measurement

The plan was to fix what the comparison measured. What was wrong was not just a value: it was the
**model**. The table mapped a **family of eight** to a fixed shape and a fixed envelope, and the
measured result is that 29 (*overdrive*), 30 (distortion), 42 (cello) and 48 (strings) came out
with the **same waveform** — 23.2% of Double Dragon's notes among the first three.

Three changes, all with the measurement as the target:

1. **The shape became continuous.** Instead of four fixed steps, the harmonic series is
   `1/k^exponent`, and each family's exponent was **tuned by sweep**: render, measure the
   centroid, compare with the soundfont's. The fixed steps were wrong precisely because the targets
   fell **between** them.
2. **The harmonic ceiling became Nyquist's.** It was 12 for saw and 9 for square and triangle.
   With `1/k^e` small enough, the high harmonics **are** the timbre: cut at 24, the sawtooth lead
   measured 2823 Hz where the real sample measures 3497 Hz.
3. **Normalization became computed per note**, sweeping 96 phases (20 µs per note), because the
   series' peak depends on the exponent **and** on the number of harmonics the note's pitch
   allows. Without this, the bass (`e = 2.45`) would come out almost three times louder than the
   lead (`e = 0.70`), and the timbre would change the music's balance along with it.

Centroid error against the soundfont, in the nine reference cases:

| case | soundfont | Zeebx before | Zeebx now | error before | error now |
|---|---:|---:|---:|---:|---:|

In Double Dragon's real music (the 47.5 s SMF): peak 0.8 (by construction, the same
`normalize()`) and RMS **0.159**, against **0.1488** for the soundfont — it was 0.1459.

**A robustness defect showed up along the way.** When measuring the SMF extracted from the `.ggz`,
the duration came out **168 s** where the game plays 47.5 s: the parser scanned every `MTrk` chunk
in the buffer, and the extracted member carries the following songs glued on. The game delivers
one SMF per `Play`, so the defect does not show in-game — but any file with two concatenated songs
yielded a wrong duration, which is the least noticeable symptom. Now reading stops at the number
of tracks the header declares.

Four tests pin what was fixed, each one failing on the previous code: distortion cannot be the
same waveform as *overdrive*; lead 81 has even harmonics (sawtooth) and 80 does not (square); the
bass decays instead of staying flat; and two glued songs do not become one.

**What is still left out, measured:** the harmonic ratio of strings (8.37 in the real sample
against the 0.6 a `1/k^e` series can reach), that of distortion (4.58 against 0.84), the drums'
centroid (6661 against 7092 Hz, because filtered noise lacks a drum's resonance) and the shimmer
of a string section (the bank's tremolo and chorus). That is sample material, and it is the
subject of the next stage — the wavetable with `rustysynth`.

### Stage 2 done: the sample bank, optional, with fallback

The timbre table reached the limit of what a sum of harmonics can do. What is missing is **sample
material**, and for that a SoundFont synthesizer came in: `rustysynth`, MIT and pure Rust.

**Why `rustysynth` and not Zeebulator's code.** Even with the license compatible, the common path
still uses `rustysynth`, because it is MIT, pure Rust and works for every build.

**Why the bank is not embedded.** It is 32 MB (GeneralUser GS measures 32,319,396 B) and loading
takes +64 MiB of RSS, because the samples become `float`. Embedded, the core's `.so` would go from
15.6 MB to ~48 MB across six CI targets — 48 MB to run a 1 MB game does not pay for itself. The
bank is looked for in `<device root>/soundfonts/*.sf2`, and `ZEEBX_SOUNDFONT` points straight at a
file.

**Without a bank, nothing changes.** MIDI falls back to the timbre table, and the report says which
of the two paths played, through the assumption in use. `rustysynth` is pure Rust: the core still
has zero host dependencies, and `ldd` only shows libstdc++, libgcc, libm and libc.

Measured **on the twelve songs** in the package, not on just one: each SMF was extracted from
`sound.ggz` and rendered through the three paths, with a 1 s window at 40% of each song's length.

| render | mean centroid error | worst case | best case |
|---|---:|---:|---:|
| **Zeebx with the sample bank** | **11.3%** | 27.2% | 0.2% |
| Zeebx with the timbre table | **40.3%** | 115.9% | 1.5% |

On the main and longest song (47.5 s) the numbers are better than the average — **2.5%** with the
bank against **38%** with the table —, and that is why measuring across the twelve matters: the
average is the honest answer, and it says the bank is **3.6× closer** to the reference, not that
it is the same.

What is left of the 11.3% belongs to the **synthesizer**, not the material: both play the same
samples, but `rustysynth` and TinySoundFont interpolate and handle envelopes differently, and
Zeebulator's path still goes through mono with −16 dB of headroom. It is also honest to record
that the table nails two songs (1.7% and 1.5%) and badly misses two others (114.7% and 115.9%):
the approximation is not uniformly bad, it depends on which instruments the music uses.

Two defects showed up in the measurement, both by comparison with the reference:

1. **The length ceiling was 36 s on one path and 300 s on the other**, and the 47.5 s song came
   out cut on the bank path. Two paths that claim to play the same score cannot have different
   ceilings. Now both use the same one.
2. **The level was not the same.** The table leaves the peak at 0.8 (see `midi::normalize`) and
   the bank came out at 0.53: the same song changed volume depending on whether the device had a
   `.sf2` installed or not, and in-game that shifts the balance between the soundtrack and the
   effects, which go through the same mixer. Now the bank normalizes the same way.

Measured cost: loading the bank plus rendering the 47.5 s song takes **295 ms**, once per song and
with the bank kept per path (the game plays twelve).

#### Which bank to use: measured, not picked by taste

Four candidates, with what was verified at a primary source (size by `HEAD` on the file, license
from the Debian package's `copyright` or from the author's repository):

| bank | size | license | presets | centroid against the reference |
|---|---:|---|---:|---:|
| **GeneralUser GS** | 32.3 MB | permissive, but the text admits the unknown origin of some samples | **287** | **+2.5%** |
| FluidR3_GS | 2.4 MB | **MIT** (Frank Wen, in Debian's `copyright`) | **33** | +7.3%, with 3× lower RMS |
| FluidR3_GM | 114 MB | **MIT** | — | not measured: too big to distribute |
| MuseScore_General (Lite) | 32.6 MB | **MIT** | — | **not read**: it is `.sf3`, and `rustysynth` rejects SF3 (there is a test in the crate itself) |

The small bank **does not solve it**, and the reason is measured: FluidR3_GS has 33 presets
because it is a GS subset, and Double Dragon's music uses **25 different GM programs**. With 33
presets, most fall onto the default preset, and the result is a thinner mix (RMS 0.055 against
0.143 for GeneralUser, with the same 0.8 peak). It is still 7.3% better than the table, but it
falls far short of the full bank.

In other words: **fidelity and a clean license do not fit together in the same size**. GeneralUser
GS is the reference Zeebulator uses and the one that gets to 2.5%; its license allows
redistribution, but the text itself says the origin of all the samples is not known. Whoever
publishes has to decide that. An open path: `rustysynth-ext` reads SF3, and then
MuseScore_General (MIT, 32.6 MB) comes in — not tested here.

#### The production path, proven by the report

The module has its own test, but what matters is the path the game takes:
`Machine::decode_sound` → `play_with_bank` → `soundfont::play`. Measured with the scan pointed at
Double Dragon, 30 virtual seconds, same ROM:

```text
without bank     assumption: "MIDI music is synthesized here, with approximate timbre"
                 audio: rms 0.1511
with bank        assumption: "MIDI music is played with the device's sample bank"
                 audio: rms 0.1375
```

The assumption line is the proof: it only appears when the bank **went in**, and it is written in
the game's report, not in the test. And the RMS changes along with it — 9% lower, which is the
bank swapping the material.

**A note that avoids confusion on the next scan:** the scan of the 62 ROMs runs with
`--no-default-features`, and the `soundfont` feature is **not** on there. That is on purpose: the
baseline summary has no audio, and turning the bank on would only change the numbers in the full
report. Anyone who wants to see the bank's effect on the scan needs to pass `--features soundfont`
**and** point `ZEEBX_SOUNDFONT`; without either of the two, the path is the timbre table's.

#### The core says where the bank should go

The search is by directory, and the folder comes from the system root the frontend provides —
whoever installs the core has no way to guess. So the core **says it**, in the log, in one line.
Measured on this machine's RetroArch (1.20, `glcore` driver):

```text
without bank  Zeebx: no MIDI sample bank; the soundtrack plays with the wavetable.
              To hear it with samples, put a .sf2 in
              /home/…/RetroArch/system/zeebx/aparelho/soundfonts (or point ZEEBX_SOUNDFONT at one)

with bank     Zeebx: MIDI sample bank at
              /home/…/RetroArch/system/zeebx/aparelho/soundfonts/GeneralUser-GS.sf2;
              the soundtrack plays with the samples
```

The choice to **warn** instead of adding one more search directory is deliberate: one more path is
a guess, and a guess in a file path is paid for with "it doesn't work and doesn't say why". The
build without the feature also answers — saying it does not have the synthesizer —, because
silence here leads to the same wrong conclusion.

#### Choosing the bank: the firmware's, when someone has it

The console has its bank in the firmware, which we have not read yet, and the difference in
instruments you hear against the device may come from there. For anyone who has the firmware's
`.sf2` — or just prefers another bank — the choice is per frontend, and applies from the next game
opened, because the bank is opened when the machine is born (`soundfont::set_soundfont`):

| frontend | where it is chosen |
|---|---|
| Qt and egui | Settings › Audio, with "Choose…" and "Use automatic" |
| Android | Settings › Audio, through the app's own folder browser |
| headless | `[audio] soundfont = PATH` in `config.ini`, or `--soundfont=PATH` |
| Libretro | the `zeebx_soundfont` option, with the `.sf2` files from the device's bank folder |

Libretro lists instead of asking for a path because a core option is a fixed list of values.

The search becomes: the chosen one, then `ZEEBX_SOUNDFONT`, then the first `.sf2` in the folder. A
chosen bank that has disappeared becomes a warning in the log, and the search goes on.
`ZEEBX_SOUNDFONT` was ignored until now — only a function nobody called read it —, even though the
"no bank" warning told people to use it.

#### Reverb and chorus: the score sets the dose

The bank played with `enable_reverb_and_chorus = false`, on the argument that the console sounds
dry. That was not measured, and turning it off had a side effect: the score says per channel how
much reverb (CC91) and chorus (CC93) each instrument gets, and without the effects unit those
controllers fell into the void. Every note ended dry, which sounds like a cut-off release.

Now the effects are on by default, and every frontend has a way to turn them off
(`soundfont::set_effects`, which applies from the next game): Settings › Audio in Qt and egui,
Settings › Audio on Android, `[audio] midi_effects` in headless and `zeebx_midi_efeitos` in
Libretro.

#### The cost of rendering the music, and the defect it revealed

Measured with the same song (Double Dragon, 47.5 s), in `--release`, on this machine:

| path | bank load | render the whole song |
|---|---:|---:|
| timbre table | — | **6.25 s** |
| sample bank (GeneralUser GS, 32 MB) | 23 ms | **289 ms** |

The bank is **21× faster**, and that was not expected. The reason is the work per sample: the
table sums `sin()` per harmonic **for every sample** (up to 48 harmonics × 1,057,823 samples),
while the bank plays recorded samples with interpolation.

**The defect this revealed is more serious than the fidelity difference.** Synthesis happens inside
API dispatch, in the game's `Play` call: with the table, every song that starts **freezes the game
for 6.25 s** on this machine — and the device is much slower than it. Double Dragon plays twelve
songs. With the bank the same stretch takes 289 ms, which is still noticeable, but a different
order of magnitude.

**Fixed, and the fix was the classic one for additive synthesis**: one sine cycle is computed
**once**, and each harmonic is read from that same cycle at `k` times the speed — so each harmonic
costs one read, not one `sin()`. The wave is kept per `(exponent, number of harmonics)`, and the
voices of a song share the same tables (a few hundred distinct pairs for 1788 notes).

| | before | after |
|---|---:|---:|
| render 47.5 s of music | 6.25 s | **183 ms** |
| centroid error against the soundfont | 701 Hz | **699 Hz** |

In other words: **34× faster**, with the timbre intact — the 2 Hz difference is the quantization
of a 1024-point table, and linear interpolation between neighboring points keeps high notes free
of hiss. And the table path became **faster than the bank's** (183 ms against 289 ms), which
reverses the cost comparison between the two: the bank still wins on fidelity, not on time.

A second possible fix was left out: rendering in chunks, spreading the cost over the following
frames. The mixer already has a stream voice (`open_stream`/`feed_stream`) for sound the game
delivers bit by bit, but the sequencer would have to survive between calls, and that touches the
save state. At 183 ms per song, it does not pay for itself.

#### The other two games that use MIDI, and an assumption the measurement knocked down

Three games in the collection deliver their soundtrack as MIDI: Double Dragon, Ultimate Chess 3D
and Zuma's Revenge. The last two carry **one** short SMF each (326 B in format 1 with six tracks,
and 228 B in format 0), hidden in their own containers — `.sar` and `.dat`, both with `MThd` in the
middle.

Measured against the same reference:

| song | reference | timbre table | error |
|---|---:|---:|---:|
| Ultimate Chess 3D | 583 Hz | 499 Hz | 14.4% |
| Zuma's Revenge | 3703 Hz | 3373 Hz | 8.9% |

In other words, **9% to 14%** in these two, against the 40% average in Double Dragon. It is not a
contradiction: the approximation's error depends on **which instruments the music uses**, and
Double Dragon uses 25 GM programs, with 23% guitars — exactly where the table confused 29, 30, 42
and 48.

**The assumption that fell.** In Chess the energy (RMS) of our render came out **twice** the
reference's, and the easy reading was "peak normalization is compressing everything to the same
volume". Measured: **no**. The raw peak of the sum comes out at 2.64 and 6.59 in these two games, so
normalization **always attenuates** (factors 0.30 and 0.12) — it never amplifies. What differs is
the reference's level, which varies per song (0.78 in Double Dragon, about 0.42 in Chess), while
ours is fixed at 0.8 by construction.

It stays as it is, and the reason is honest: the hardware's level is not known — Zeebulator's path
applies −16 dB of headroom by its own choice, not by a measurement of the console —, and a fixed
peak is what avoids clipping when the music goes into the same mixer as the effects. Swapping that
for a guess would not be fidelity, it would be another choice.

### A game's `IAStream` as a source

Aviãozinho, a fan-made Quake port, builds the `ISource` another way: it writes its own `IAStream`,
whose `Read` returns what Quake's mixer has just mixed, and asks `ISourceUtil` (slot 6) to turn it
into an `ISource`. That slot only accepted an open `IFile` and refused the rest; `SNDDMA_Init` gave
up, and `S_Init` read `shm->speed` from the null buffer and crashed the game at 24 ms. The `Read`
of `IAStream` and that of `ISource` are in the same slot, with the same arguments and the same
return, so the stream itself is returned as the source, and the stream voice calls the game's code
as it already did with the arcade ports. The format comes in the usual `AEEMediaWaveSpec`:
22050 Hz, stereo, 16-bit.

## What is missing

**The console's instrument bank.** With it, MIDI stops being an approximation and sounds the way
it used to — and the path to it is the same as for the missing classes: the EFS2 reader (see
[14](14-z-wheel-and-efs2.md) and [15](15-whats-missing-from-the-nand.md)).

Until the console's bank turns up, the fidelity reference is the measured comparison: the
wavetable with `rustysynth` and a General MIDI bank installed next to the core. What is missing is
**a default bank** to distribute — GeneralUser GS works and its license allows it, but its text
admits the unknown origin of some of the samples, so whoever publishes needs to decide that with
their eyes open.
